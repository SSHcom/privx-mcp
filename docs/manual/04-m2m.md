# Configure machine-to-machine access

Use this path when a client authenticates with a long-lived service secret instead of an OIDC access token. A service secret is a random string you generate, map to one PrivX user, and give to one machine.

## 1) Run a separate process for `m2m`

A server process runs in one auth mode, either `oauth` or `m2m`. Set `server.auth_mode = "m2m"` on the process that machine clients call, and keep a separate `oauth` process for browser clients, including privx-mcp-proxy.

A config file that mixes both fails startup, so leave `[oauth]` out of the `m2m` file.

The mode only changes how the caller is identified. Everything after that is the same as `oauth`:

- the server mints a 90-second JWT with `rsa_key_file`
- it exchanges that JWT with PrivX
- it runs tools as that PrivX user
- role filtering uses the separate API client

The RSA key and the four `[privx_auth]` API credentials stay required.

## 2) Generate the secrets and map them to users

`server.service_secrets` holds every mapping in one string:

- `|` separates mappings
- the first space in a mapping separates the username from the secret
- a secret is at least 32 characters, and no two mappings share one
- a username may repeat, which is how you rotate: both secrets work until you remove the old one and restart

Startup rejects a string that breaks these rules. [MCP server configuration](reference/server/SERVER.md) lists the checks. Usernames are plain PrivX usernames; a DN does not fit this format.

Generate one secret per machine:

```bash
openssl rand -hex 32
```

Then set the mappings in `privx-mcp-config.toml`:

```toml
[server]
auth_mode = "m2m"
public_url = "https://mcp.example.net:8181"
service_secrets = "svc-ci <secret>|svc-nightly <secret>"
```

`SERVER_SERVICE_SECRETS` replaces the whole `service_secrets` value when it is set. Prefer the environment variable in production, so the secrets stay out of the config file:

```bash
SERVER_SERVICE_SECRETS='svc-ci <secret>|svc-nightly <secret>'
```

After loading, the process keeps only each username and the SHA-256 of its secret. Startup logs the mode, the mapping count, and the usernames. Neither the secrets nor the `Authorization` header appear in any log.

## 3) Keep the bearer on TLS

The secret travels as a bearer token on every request. Prefer an `https` `public_url`. Plain `http` is allowed when TLS ends at a reverse proxy in front of this process; startup then logs that the URL is NOT HTTPS and the bearer travels in CLEARTEXT.

## 4) Bind each machine to its own PrivX user

The client sends `Authorization: Bearer <secret>` to `/mcp`, usually configured as a static header on the server entry. A typical client config looks like this, though the exact keys and file vary by client:

```json
{
  "mcpServers": {
    "privx-mcp-m2m": {
      "url": "https://mcp.example.net:8181/mcp",
      "headers": {
        "Authorization": "Bearer <secret>"
      }
    }
  }
}
```

The server hashes the presented secret and compares it with the stored hash of each mapping: exactly one match succeeds, anything else is `401`. The secret alone decides the user: a client can only act as the users whose secrets it holds, and the request carries no other way to name one.

On a match the caller is the username from that mapping, used as-is:

- identity mapping rules such as `strip-domain` do not apply
- a value containing `@` matches the PrivX email and Windows account
- any other value matches the PrivX principal
- `permissions.source_type` and the External Token Provider users directory must name that account's directory

PrivX roles still limit which tools work, so a secret mapped to a read-only user cannot gain writes from the server config. PrivX audit records the username, not which secret was used, so give each machine a dedicated service user with the minimum role. A secret mapped to a human admin is a password with no MFA and no expiry.

## 5) Revoke by editing the mapping and restarting

A service secret never expires and the IdP knows nothing about it, so disabling the person there has no effect. It works until you remove its mapping and restart the process. Treat it like `api_client_secret`.

If a client's secret leaks, the damage is limited to that one mapped user.

## 6) Validate

Start the server and call `/mcp` with a configured secret:

```bash
curl -i -H "Authorization: Bearer <secret>" https://mcp.example.net:8181/mcp
```

The same request without the header is `401`. Then run one read tool as that service user and confirm PrivX audit names that user.
