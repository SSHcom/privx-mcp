# Configure machine-to-machine access

Use machine-to-machine access when a client cannot run the browser-based OAuth flow. There are two modes:

| Mode      | Client sends                                         | Identity comes from                          |
| --------- | ---------------------------------------------------- | -------------------------------------------- |
| `m2m`     | `Authorization: Bearer <secret>`                     | The service secret, mapped to one PrivX user |
| `m2m-jwt` | `X-API-KEY: <key>` and `Authorization: Bearer <jwt>` | A claim in the JWT, mapped to one PrivX user |

**Pick** `m2m-jwt` when the user has already been authenticated before the MCP client runs. Another component, such as a gateway or a backend service, obtains the JWT through OAuth or any other flow and hands it to the MCP client, so the client never runs a login itself. 

**Pick** `m2m` when a simpler approach is acceptable, for example when obtaining a JWT does not fit into the client's flow and each machine can hold its own long-lived secret.

> **Note**
>
> The MCP server can only support a single authentication mode at a time.  
> Everything after authentication (oath, m2m or m2m-jwt) works the same.
>
> **Never use m2m authentication for end user scenarios.** If a user secret or API key is accidently shared, it can allow anyone with awareness of PrivX user names to log in.

### Generating secrets

Both machine-to-machine modes need at least one secret/key

If your organization does not already issue these, you can generate them with one of the following commands:

- `openssl rand -hex 32`
- `tr -dc A-Za-z0-9 </dev/urandom | head -c 64; echo`

This prints 64 hex characters, which meets the minimum length of both a service secret (32) and an API key (12). Prefer setting secrets through environment variables in production, so they stay out of the config file. After loading, the process keeps only the SHA-256 of each secret or key, and neither the values nor the request headers appear in any log.

## `m2m` mode

### Map secrets to users

In this mode authentication is configured by a secret to user mapping.

- The `[server].m2m_identity_mapper` configuration parameter holds user mappings in one string.
  - Entries are separated by the `|` (pipe) character.
  - Each entry is `<privx username> <secret>`
  - Example: `m2m_identity_mapper = "john.doe Auxkb4Uv7qYa...|jane.doe b29c5baDL1f..."`
- A username may repeat, which is how you rotate: both secrets work until you remove the old one and restart

Example pattern when using a configuration file in TOML format:

```toml
[server]
auth_mode = "m2m"
m2m_identity_mapper = "<privx username> <secret>|<privx username> <secret>|etc"
```

Example pattern when using environment variables:

```bash
SERVER_AUTH_MODE="m2m"
SERVER_M2M_IDENTITY_MAPPER="<privx username> <secret>|<privx username>|etc"
```

### Configure the client

The client sends `Authorization: Bearer <secret>` to `/mcp`, usually configured as a static header on the server entry. A typical client config looks like this, though the exact keys may vary by client:

```json
{
  "mcpServers": {
    "privx-mcp-m2m": {
      "url": "https://mcp.example.net:8181/mcp",
      "headers": {
        "Authorization": "Bearer <secret>"
      }
    }
  }
}
```

### How it works

- The server hashes the presented secret and compares it with the stored hash of each mapping: exactly one match succeeds, anything else ends with a `401` response.
  - The user of a mapping identifies a PrivX user.
  - On tool calls permissions of the PRivX user is observed
- A secret is valid until replaced

## `m2m-jwt` mode

### Map claims to users

In this mode authentication is configured by a shared key and a claim to user mapping.

- The `[server].m2m_jwt_key` configuration parameter holds one shared key.
  - The key must be at least 12 characters.
- The `[server].m2m_jwt_issuer` configuration parameter is optional. When set, it must equal the token's `iss`.
- The `[server].m2m_jwt_identity_mapper` configuration parameter holds user mappings in one string.
  - Entries are separated by the `|` (pipe) character.
  - Each entry is `<claim> <value> <privx username>`, with a space between the three fields. `<claim>` can only be `preferred_username` or `email`.
  - Example: `m2m_jwt_identity_mapper = "preferred_username jdone john.done|email john.done@example.com john.done"`
- A username may repeat. The same claim and value may not.

Example pattern when using a configuration file in TOML format:

```toml
[server]
auth_mode = "m2m-jwt"
m2m_jwt_key = "<key>"
m2m_jwt_issuer = "<issuer>"
m2m_jwt_identity_mapper = "<claim> <value> <privx username>|<claim> <value> <privx username>|etc"
```

Example pattern when using environment variables:

```bash
SERVER_AUTH_MODE="m2m-jwt"
SERVER_M2M_JWT_KEY="<key>"
SERVER_M2M_JWT_ISSUER="<issuer>"
SERVER_M2M_JWT_IDENTITY_MAPPER="<claim> <value> <privx username>|<claim> <value> <privx username>|etc"
```

### Configure the client

The client sends `X-API-KEY: <key>` and `Authorization: Bearer <jwt>` to `/mcp`, usually configured as static headers on the server entry. A typical client config looks like this, though the exact keys may vary by client:

```json
{
  "mcpServers": {
    "privx-mcp-m2m-jwt": {
      "url": "https://mcp.example.net:8181/mcp",
      "headers": {
        "X-API-KEY": "<key>",
        "Authorization": "Bearer <jwt>"
      }
    }
  }
}
```

### How it works

- The server hashes the presented key and compares it with the stored hash: a missing or wrong key ends with a `401` response.
- The JWT is parsed without a signature check. A missing or past `exp` ends with a `401` response, and, when `m2m_jwt_issuer` is set, so does an `iss` that does not match it exactly.
- Exactly one mapping whose claim equals the token value succeeds, anything else ends with a `401` response.
  - The username of a mapping identifies a PrivX user.
  - On tool calls permissions of the PrivX user are observed
- A key is valid until replaced. To remove one user's access, delete their mapper rows and restart.
- Because the signature is not checked, anyone who has the API key can present a JWT with any mapped claim and act as that user.

## Security concerns

In both machine-to-machine modes, the practical security boundary is the shared secret material. In `m2m` mode this is the bearer secret. In `m2m-jwt` mode this is the `X-API-KEY`.

For `m2m-jwt`, the JWT is parsed without signature verification. The `exp` requirement and optional `iss` check are policy checks only, not cryptographic proof of identity. They help reject malformed or stale tokens, but they do not protect against token forgery by someone who already has the API key.

The user-mapping configuration limits blast radius in both modes. Access is limited to configured mapper entries: a caller can only become a PrivX user that is explicitly mapped, and unmapped identities are rejected.

This model is common among MCP deployments that use static header credentials (`Authorization` bearer tokens, API keys, or both) between trusted components.

The server cannot assume every machine-to-machine environment has network reachability to an external signing authority. Some deployments run agents and MCP servers in shielded or black-boxed networks. Because of that, this mode does not require live JWT signature-authority access.

Operators must treat machine-to-machine credentials like privileged secrets and keep them out of end-user workflows. If a secret or API key is shared in an end-user scenario, impersonation of mapped users becomes possible. It is the operator's responsibility to re-issue secrets or API keys, restart the MCP server to apply the new values, and maintain a secure process for issuing JWTs.
